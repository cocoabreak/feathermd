# 要求定義: Windows性能ベースライン (windows-performance-baseline)

## 背景・動機

FeatherMDでは、Shikiの言語限定、KaTeX・Mermaidの遅延ロード、Shikiウォームアップなど、個別の計測に基づく軽量化を行ってきた。一方、アプリ全体の配布サイズ、初期チャンク、起動、Markdown初回表示、再表示、メモリを同じ条件で比較する基準がない。機能や依存関係を追加したとき、体感と配布物へ与えた影響を継続して判断できるWindows基準の計測手順とベースラインを整備する。

## スコープ

- **対象**: Windows x64、productionフロントエンド、Tauri release実行ファイル、Windows向け配布物、Vite出力、通常MarkdownとリッチMarkdown、起動・描画時間、プロセスツリーのメモリ、CIでのサイズ回帰検知、ローカルWindowsでのリリースQA
- **対象外**: Linux/macOS間の比較、hosted runner上の時間・メモリを厳格な合否基準にすること、大容量Markdown描画の仮想化・ストリーミング化、計測結果を伴わない機能・依存関係の削減
- 初回は計測基盤と現行値の記録までを対象とし、個別の軽量化は結果に基づく後続Issueで扱う

---

## ユーザーストーリー

### US-001: 再現可能なWindows基準環境

As a メンテナー
I want to 同じ条件で性能計測を再実行できる
So that リリースや変更間の差を説明できる

**受け入れ条件**

- [ ] Windows、CPU、メモリ、ストレージ、WebView2、Node.js、Rust、ビルド種別など、結果の解釈に必要な環境情報を記録する
- [ ] コールド起動とウォーム起動、初回表示と再表示の定義を明記する
- [ ] 計測前のビルド、アプリ状態、WebViewプロファイル、fixture、バックグラウンド条件を固定する
- [ ] 通常利用中のFeatherMDが起動している場合は計測を開始せず、既存プロセスやその状態を変更しない
- [ ] 時間指標は複数回計測し、個別値と中央値を記録する
- [ ] 計測失敗、タイムアウト、外れ値の扱いを明記し、失敗値を成功結果へ混ぜない
- [ ] 同じコミットと環境で手順を再実行し、同じ形式の結果を生成できる

### US-002: 配布物とフロントエンドサイズの把握

As a メンテナー
I want to 配布物と初期ロード資産のサイズを確認したい
So that 機能追加によるサイズ増加の原因を追跡できる

**受け入れ条件**

- [ ] Windows向け実行ファイル、MSI、NSIS、portable ZIPについて、存在する成果物のファイルサイズを記録する
- [ ] Vite出力全体とJavaScript・CSS・画像・フォント等の種別ごとの合計サイズを記録する
- [ ] 初期HTMLから静的に参照される初期ロード資産と、KaTeX・Mermaid・Shiki等の遅延チャンクを区別する
- [ ] 主要チャンクはファイル名、rawサイズ、圧縮サイズを記録する
- [x] 同一条件のベースラインとの差分を機械可読な形式で算出できる
- [ ] GitHub Actionsで再現性の高いフロントエンドサイズを計測し、結果artifactを保存する

### US-003: 起動とMarkdown表示時間の把握

As a メンテナー
I want to 起動と代表文書の表示時間を計測したい
So that ユーザーが待つ主要区間のコストを特定できる

**受け入れ条件**

- [ ] productionと同じrelease最適化を使う隔離済み計測ビルドについて、コールド起動とウォーム起動を分け、プロセス開始から空状態のWebViewが操作可能になるまでを計測する
- [ ] 小規模な通常Markdownの初回表示時間を計測する
- [ ] コードブロック、KaTeX、Mermaidを含むリッチMarkdownの初回表示時間を計測する
- [ ] 同じ実行中に同一種別の文書を再表示した場合の時間を初回表示と分けて計測する
- [ ] 文書表示完了は固定sleepではなく、本文および非同期レンダラーの完了状態で判定する
- [ ] devビルドとreleaseビルドを混同せず、ベースラインはreleaseビルドを主指標とする

### US-004: メモリ使用量の把握

As a メンテナー
I want to 代表状態ごとのメモリ使用量を計測したい
So that WebViewを含む実際の常駐コストを把握できる

**受け入れ条件**

- [x] 空状態、通常Markdown表示後、リッチMarkdown表示後のメモリを記録する
- [x] Tauri親プロセスだけでなく、その時点のWebView2を含むプロセスツリー全体を集計する
- [x] 指標名とWindows API上の意味を明記し、ワーキングセットとプライベートメモリ等を混同しない
- [x] 描画完了後の一定条件を満たした時点で採取し、対象PIDと子プロセス数を結果へ含める
- [x] 計測対象が終了または入れ替わった場合は値を欠損として扱い、部分的な集計を正常値にしない

### US-005: 継続的な比較と軽量化判断

As a メンテナー
I want to ベースラインと現在値を比較したい
So that 効果のある改善だけを優先できる

**受け入れ条件**

- [x] 機械可読なJSON結果と、人が確認できるMarkdownサマリーを生成する
- [ ] 結果へcommit、アプリバージョン、計測日時、環境、各試行値、中央値を含める
- [x] 初回導入時はCI結果をレポートとして扱い、計測値と変動幅を確認してからサイズ上限を設定する
- [ ] 上限設定後は、初期ロードまたは総バンドルサイズの大幅な回帰をCIで検出できる
- [ ] 時間・メモリはWindows実機のリリースQAで比較し、hosted runnerの揺らぎだけでCIを失敗させない
- [ ] 主要コスト要因と軽量化候補を効果、リスク、実装コストで順位付けし、後続Issueまたは見送り理由を残す
- [ ] 計測用コードや固定fixtureが通常のproductionバンドルへ混入しない
- [ ] 計測ビルドは通常版と異なるidentifier、AppData、single-instance名前空間を使用し、通常版の設定、タブ、履歴、信頼済みルートを読み書きしない

## 非機能要求

- 計測runnerはタイムアウトを持ち、成功・失敗にかかわらず起動したプロセスと一時状態を後始末する
- single-instance経路が通常利用中のFeatherMDへfixtureを送らないよう、起動前に既存インスタンスがないことを確認し、競合時はfail-closedに停止する
- プロセス終了時はPIDだけを所有根拠にせず、起動時に記録した作成時刻、実行ファイル、親子関係を再検証し、PID再利用または不一致時は強制終了しない
- 計測対象を安定させるため外部ネットワークへ依存せず、fixtureは決定的に生成または管理する
- 計測結果へMarkdown本文、実在するローカル絶対パス、OSユーザー名などの個人環境情報を保存しない
- CIで比較するサイズ指標はOSや実行タイミングの影響が小さく、同一ビルド出力から決定的に算出できるものに限定する
- リリースQAの時間・メモリ結果には環境差があることを明示し、異なる基準環境同士を単純比較しない

## 未決定事項（設計フェーズで決定）

- [x] 既存WebView2スモークへ統合するか、性能計測runnerを分離するか
- [x] 起動・表示完了をproductionビルドでどう観測するか
- [x] メモリを親プロセスだけでなくプロセスツリーで集計するか
- [x] CIで時間・メモリを合否判定へ使うか
- [x] 初回から固定上限を設けるか、ベースライン確定後に導入するか
- [x] 結果形式とリポジトリへ保持する情報の境界
